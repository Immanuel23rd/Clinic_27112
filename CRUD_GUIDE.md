# Clinic Project: Code Explanation and CRUD Guide

This guide describes the project as it is implemented now. The extra queries added for Practical Exercise 4
and for the JPA & JPQL quiz are documented in `ASSIGNMENT_IMPLEMENTATION.md`.

## 1. Project overview

A **Spring Boot 4.1.1 + Spring Data JPA (Hibernate) + PostgreSQL** REST application on **Java 17**,
built with the Maven wrapper (Maven 3.9.16).

```text
kigali.clinic.rw
├── ClinicApplication.java        # Spring Boot entry point
├── domain/                       # JPA entities + AppointmentStatus enum
│   ├── Patient, Doctor, Office, Specialization, Appointment
├── repository/                   # Spring Data interfaces (one per entity)
├── service/                      # Business rules + ResourceNotFoundException, RelationshipConflictException
└── controller/                   # REST controllers, ClinicQueryController, GlobalExceptionHandler
```

Request flow:

```text
HTTP request -> Controller -> Service -> Repository -> PostgreSQL
```

For example, `POST /api/doctors` reaches `DoctorController`, which calls `DoctorService.create`. The service
resolves the office and specializations by ID, applies the rules in section 5, and saves through
`DoctorRepository`. Hibernate generates the SQL, and the controller answers `201 Created` with a `Location` header.

## 2. Configuration

### `pom.xml`

| Dependency | Purpose |
|---|---|
| `spring-boot-starter-webmvc` | REST controllers |
| `spring-boot-starter-data-jpa` | JPA, Hibernate, repositories |
| `spring-boot-starter-validation` | Bean Validation (`@Valid`), see the limitation in section 10 |
| `spring-boot-starter-actuator` | Health and metrics endpoints |
| `postgresql` (runtime) | JDBC driver |

`java.version` is **17**, so a JDK 17 (or newer) with `javac` is needed to build.

### `application.properties`

```properties
spring.application.name=clini
spring.datasource.url=jdbc:postgresql://localhost:5432/clinic
spring.datasource.username=postgres
spring.datasource.password=postgres
spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true
server.port=8081
```

- The app listens on **port 8081**, so every example URL below uses `http://localhost:8081`.
- `ddl-auto=update` lets Hibernate create and alter tables, which is convenient for learning.
  A migration tool such as Flyway or Liquibase is safer for production.
- `show-sql=true` prints each generated statement. Read it when a query returns unexpected rows.
- The database password is stored in plain text. Keep real credentials out of Git by reading them from
  environment variables:

```properties
spring.datasource.url=${DB_URL:jdbc:postgresql://localhost:5432/clinic}
spring.datasource.username=${DB_USERNAME:postgres}
spring.datasource.password=${DB_PASSWORD}
```

## 3. Domain model

| Entity (table) | Fields | Relationships |
|---|---|---|
| `Patient` (`patient`) | `id` (UUID), `firstName`, `lastName`, `dateOfBirth` | One-to-many `appointments` (inverse side) |
| `Doctor` (`doctor`) | `id` (UUID), `firstName`, `lastName`, `dateOfBirth` | One-to-one `office` (owner, `office_id`, unique); many-to-many `specializations` (owner, join table `doctor_specialization`); one-to-many `appointments` (inverse) |
| `Office` (`office`) | `id` (UUID), `name`, `officeNumber` (int) | One-to-one `doctor` (inverse) |
| `Specialization` (`specialization`) | `id` (UUID), `name` (not null, unique) | Many-to-many `doctors` (inverse) |
| `Appointment` (`appointment`) | `id` (UUID), `appointmentDate`, `reason`, `status` | Many-to-one `patient` and `doctor` (owner, `patient_id`, `doctor_id`) |

`AppointmentStatus` is stored as text (`EnumType.STRING`) and has the values
`PENDING`, `SCHEDULED`, `CONFIRMED`, `COMPLETED`, `CANCELLED`.

All primary keys are UUIDs generated by Hibernate (`GenerationType.UUID`), so each entity exposes `getId()`
but no `setId`.

### Which side owns a relationship

The side with the `@JoinColumn` or `@JoinTable` owns the foreign key, and only changes on that side are written:

```java
// Doctor owns the Doctor-Office link, so the service must call this...
doctor.setOffice(office);
doctorRepository.save(doctor);
// ...calling office.setDoctor(doctor) alone would NOT change office_id.
```

For the same reason `SpecializationService.delete` removes the specialization from each doctor's list
(the owning side) before deleting the row.

### Dates

`Patient`, `Doctor` and `Appointment` store dates as `java.sql.Date`. In JSON they are written and read as
`"yyyy-MM-dd"`, for example `"2000-05-20"`. The quiz endpoints convert `LocalDate` text to `java.sql.Date` in the controller.

### JSON recursion guards

Bidirectional relationships would serialize forever, so the inverse side is hidden with `@JsonIgnore`:
`Doctor.appointments`, `Patient.appointments`, `Office.doctor`, `Specialization.doctors`.
A doctor's JSON therefore contains its `office` and `specializations`, but not its appointments.

## 4. Repositories

Each entity has a `JpaRepository<Entity, UUID>`, which supplies `save`, `findAll`, `findById`,
`existsById`, `delete` and `deleteById`. Custom methods:

| Repository | Custom methods |
|---|---|
| `PatientRepository` | `findByLastNameIgnoreCaseOrderByFirstNameAsc`, `findPatientsOfDoctor` (JPQL), `findFrequentPatients` (JPQL) |
| `DoctorRepository` | `findBySpecializationName` (JPQL), `findDoctorsWithoutOffice` (JPQL) |
| `OfficeRepository` | `findByName`, `findByNameAndOfficeNumber(String, int)`, `findByDoctor`, `findByOfficeNumber`, `findOfficesByAppointmentCount(Pageable)` (JPQL) |
| `SpecializationRepository` | `findByNameIgnoreCase`, `findUnused` (JPQL) |
| `AppointmentRepository` | `existsByDoctorId`, `existsByPatientId`, plus the Exercise 4 and quiz queries listed in `ASSIGNMENT_IMPLEMENTATION.md` |

`existsByDoctorId` and `existsByPatientId` let services reject destructive operations with a cheap
`EXISTS` query instead of loading every appointment into memory.

## 5. Services and business rules

Services hold the rules and turn missing rows into exceptions. The common pattern:

```java
public Doctor findById(UUID id) {
    return doctorRepository.findById(id)
            .orElseThrow(() -> new ResourceNotFoundException("Doctor not found: " + id));
}
```

Update methods load the existing entity first, so an unknown ID returns 404 instead of silently creating a row.
Services are `@Transactional` at class level, and read methods are marked `readOnly = true`.

| Operation | Rule | Result when violated |
|---|---|---|
| Create/update Office | `officeNumber` must be unique | `409 Conflict` |
| Delete Office | An office assigned to a doctor cannot be deleted | `409 Conflict` |
| Create/update Doctor | The office ID must be provided and refer to an existing office | `404 Not Found` |
| Create/update Doctor | An office cannot belong to two doctors | `409 Conflict` |
| Update Doctor | Sending `office: null` cannot remove an existing assignment | `409 Conflict` |
| Create/update Doctor | Each specialization needs an ID that exists. The list is replaced as a whole | `404 Not Found` |
| Delete Doctor | Blocked while any appointment references the doctor | `409 Conflict` |
| Delete Patient | Blocked while any appointment references the patient | `409 Conflict` |
| Create/update Specialization | Name is required (trimmed) | `400 Bad Request` |
| Create/update Specialization | Name must be unique, ignoring case | `409 Conflict` |
| Delete Specialization | Allowed. It is first detached from every doctor | none |
| Create/update Appointment | Doctor and patient IDs are required and must exist | `404 Not Found` |
| Create Appointment | A missing status becomes `SCHEDULED` | none |
| Create Appointment | The doctor must not already have a non-cancelled appointment on that date | `409 Conflict` |
| Update/delete Appointment | `COMPLETED` and `CANCELLED` appointments are read-only | `409 Conflict` |

The double-booking check runs on creation only. It is not repeated in `update`, and it is not atomic,
so two simultaneous requests could both pass it. A unique constraint or locking would be needed to close that gap.

To release an office, add an explicit operation such as `unassignOffice(doctorId)` rather than treating a
missing field in a general update as a deletion, which keeps the change intentional.

## 6. REST API

Every resource uses the same conventional endpoints:

| Resource | Create | Read all | Read one | Update | Delete |
|---|---|---|---|---|---|
| Doctor | `POST /api/doctors` | `GET /api/doctors` | `GET /api/doctors/{id}` | `PUT /api/doctors/{id}` | `DELETE /api/doctors/{id}` |
| Patient | `POST /api/patients` | `GET /api/patients` | `GET /api/patients/{id}` | `PUT /api/patients/{id}` | `DELETE /api/patients/{id}` |
| Office | `POST /api/offices` | `GET /api/offices` | `GET /api/offices/{id}` | `PUT /api/offices/{id}` | `DELETE /api/offices/{id}` |
| Specialization | `POST /api/specializations` | `GET /api/specializations` | `GET /api/specializations/{id}` | `PUT /api/specializations/{id}` | `DELETE /api/specializations/{id}` |
| Appointment | `POST /api/appointments` | `GET /api/appointments` | `GET /api/appointments/{id}` | `PUT /api/appointments/{id}` | `DELETE /api/appointments/{id}` |

Appointments also accept `POST /api/appointments/save`, which behaves like the plain `POST` but reports a double
booking as a plain-text 409.

Status codes: `201 Created` (with a `Location` header) after create, `200 OK` after read or update,
`204 No Content` after delete, `400` for bad input, `404` for an unknown ID, `409` for a rule violation.

Beyond CRUD, the controllers expose these extra read endpoints (full detail in `ASSIGNMENT_IMPLEMENTATION.md`):
`/api/queries/**` (Exercise 4), `/api/patients/by-last-name`, `/api/patients/of-doctor/{doctorId}`,
`/api/patients/frequent`, `/api/doctors/by-specialization`, `/api/doctors/without-office`,
`/api/specializations/unused`, `/api/offices/busiest`, `/api/appointments/by-status`, `/api/appointments/between`,
`/api/appointments/stats/by-status`, `/api/appointments/page`, `PATCH /api/appointments/cancel-day`
and `DELETE /api/appointments/cancelled-before`.
These fixed paths do not clash with `/{id}`, because Spring prefers the more specific literal path.

Relationships are always sent as IDs, never as new embedded entities:

```json
{
  "appointmentDate": "2026-10-05",
  "reason": "Routine consultation",
  "status": "SCHEDULED",
  "doctor": { "id": "existing-doctor-uuid" },
  "patient": { "id": "existing-patient-uuid" }
}
```

## 7. Error handling

`GlobalExceptionHandler` converts exceptions into JSON bodies of the form `{"error": "..."}`:

| Exception | HTTP status | Typical cause |
|---|---|---|
| `IllegalArgumentException` | 400 | Blank specialization name, bad `page`, `size` or sort direction, `page`/`size` below 1 in `/api/queries` |
| `DateTimeParseException` | 400 | A date that is not `yyyy-MM-dd` |
| `ResourceNotFoundException` | 404 | Unknown ID, missing doctor/patient/office/specialization ID |
| `RelationshipConflictException` | 409 | Any rule violation in the table in section 5 |

Two endpoints deliberately answer with a **plain-text** body straight from the controller, as the quiz requires:
`POST /api/appointments/save` (409, `Doctor is already booked on that date`) and
`GET /api/patients/of-doctor/{doctorId}` (404, `The doctor with that id does not exist`).
Malformed JSON, a bad UUID, an unknown enum value and a missing required parameter are handled by
Spring's default 400 response.

## 8. Appointment rules in detail

- A new appointment needs an existing doctor and an existing patient. The service resolves both IDs
  through their repositories, so a client cannot create an appointment pointing at nothing.
- A missing status is saved as `SCHEDULED`.
- `COMPLETED` and `CANCELLED` appointments are historical records. They cannot be updated or deleted
  through the single-record endpoints. To cancel, update a `SCHEDULED` or `CONFIRMED` appointment to `CANCELLED`.
- The two bulk quiz operations (`cancel-day` and `cancelled-before`) run as single SQL statements and
  bypass this read-only check. See `ASSIGNMENT_IMPLEMENTATION.md` for what each one touches.
- Deleting a doctor or patient that has appointments is rejected. This preserves history. A production
  system might replace the rejection with soft deletion (an `active` flag) instead.

## 10. Build, run and test

1. Install a JDK 17 or newer (not only a JRE) and check both `java -version` and `javac -version`.
2. Start PostgreSQL and create the database:

   ```sql
   CREATE DATABASE clinic;
   ```

3. Check the credentials in `application.properties` (or set them through environment variables).
4. Build and run:

   ```bash
   ./mvnw clean test
   ./mvnw spring-boot:run
   ```

5. Import `clinic-quiz.postman_collection.json` into Postman. Run folder `0 Seed data` once, then the
   other folders. It stores the generated UUIDs in collection variables and asserts status codes
   (and the returned rows where the data allows).
6. Verify rows directly in PostgreSQL when something looks wrong.

Minimum CRUD test matrix:

| Test | Expected result |
|---|---|
| Create valid Doctor | `201 Created` and a generated UUID |
| List Doctors | `200 OK` with a JSON array |
| Get existing Doctor | `200 OK` |
| Get unknown UUID | `404 Not Found` |
| Update existing Doctor | `200 OK` with the changed fields |
| Update Doctor with `office: null` while assigned | `409 Conflict` |
| Delete unassigned Office | `204 No Content` |
| Delete Office assigned to a Doctor | `409 Conflict` |
| Delete unknown Patient | `404 Not Found` |
| Delete Doctor or Patient with appointments | `409 Conflict` |
| Create Specialization with a duplicate name (any case) | `409 Conflict` |
| Create a second non-cancelled appointment for one doctor and date | `409 Conflict` |
| Update a `COMPLETED` Appointment | `409 Conflict` |

## 11. Known limitations

These are real gaps in the current code, not planned features:

- **No Bean Validation constraints on the entities.** Several controllers declare `@Valid`, but no
  `@NotBlank` or `@NotNull` annotations exist, so `@Valid` currently rejects nothing. A request with a missing
  name is saved with a null value (except the specialization name, which the service checks).
- **Entities are used directly as request and response bodies.** DTOs would stop clients from changing
  relationships by accident and would remove the dependence on `@JsonIgnore`.
- **`java.sql.Date` instead of `java.time.LocalDate`** on the entities. The quiz controllers convert between them.
- **Lazy collections are serialized during response rendering**, which works because Spring Boot's
  `spring.jpa.open-in-view` setting is on by default. Disabling it would require fetch joins or DTOs.
- **Credentials and schema management:** the database password is plain text in `application.properties`
  and `ddl-auto=update` changes the schema automatically.
- **`ClinicApplication` has an unused import** of `org.apache.catalina.core.ApplicationContext`; remove it.
- **`OfficeService.saveOffice`** is a leftover from the original `/api/office/save` endpoint. No controller
  calls it any more.
- **Double booking is checked on create only** and is not atomic (section 5).
- **The paging endpoint's `sort` property** must be an `Appointment` field. An unknown field is not handled
  specially and produces a server error.
