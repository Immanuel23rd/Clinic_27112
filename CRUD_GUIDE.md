# Clinic Project: Code Explanation and CRUD Implementation Guide

## 1. Project overview

This is a **Spring Boot + Spring Data JPA + PostgreSQL** application.

The package structure follows a common layered architecture:

```text
kigali.clinic.rw
├── ClinicApplication.java       # Spring Boot entry point
├── domain/                      # JPA entity classes
├── repository/                  # Database access interfaces
├── service/                     # Business logic
└── controller/                 # HTTP/REST API endpoints
```

The intended request flow is:

```text
HTTP request
    ↓
Controller
    ↓
Service
    ↓
Repository
    ↓
PostgreSQL database
```

For example, creating a doctor should follow this path:

1. `POST /api/doctors` reaches `DoctorController`.
2. The controller passes the request to `DoctorService`.
3. The service validates and saves the entity through `DoctorRepository`.
4. Spring Data JPA generates the SQL and persists the row.
5. The controller returns an HTTP response to the client.

## 2. What the current code does

### `ClinicApplication`

`@SpringBootApplication` enables component scanning, auto-configuration, and Spring Boot configuration. The `main` method starts the embedded web server and the application context.

### `pom.xml`

The project uses:

- `spring-boot-starter-data-jpa` for JPA/Hibernate and repositories.
- `spring-boot-starter-webmvc` for REST controllers.
- PostgreSQL JDBC driver for database access.
- Java 21 as the configured source level.

### `application.properties`

```properties
spring.datasource.url=jdbc:postgresql://localhost:5432/clinic
spring.datasource.username=postgres
spring.datasource.password=pazofils
spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true
```

This connects to a local PostgreSQL database named `clinic`. `ddl-auto=update` asks Hibernate to modify the schema automatically. That is convenient for learning, but migrations such as Flyway or Liquibase are safer for production.

The database password should not be committed to Git. Prefer environment variables:

```properties
spring.datasource.url=${DB_URL:jdbc:postgresql://localhost:5432/clinic}
spring.datasource.username=${DB_USERNAME:postgres}
spring.datasource.password=${DB_PASSWORD}
spring.jpa.hibernate.ddl-auto=update
```

### `Doctor`

`Doctor` is a JPA entity mapped to the `doctor` table. Its fields are:

- UUID primary key generated by Hibernate.
- `firstName`, `lastName`, and `dateOfBirth`.
- One-to-one relationship with `Office`.
- Many-to-many relationship with `Specialization`.
- One-to-many relationship with `Appointment`.

The owning side of the Doctor–Office relationship is `Doctor`, because it contains:

```java
@JoinColumn(name = "office_id")
private Office office;
```

The `Office.doctor` field is the inverse side because it uses `mappedBy = "office"`.

### `Office`

`Office` is mapped to the `office` table and contains a name and an integer office number. It has the inverse side of the one-to-one Doctor–Office relationship.

### `Patient`

`Patient` is mapped to the `patient` table. It has a one-to-many relationship with appointments. `Appointment` owns that relationship through its `patient_id` foreign key.

### `Appointment`

`Appointment` is related to both `Patient` and `Doctor` through `@ManyToOne` fields. This matters when deleting a doctor or patient: existing appointments may prevent deletion or become orphaned unless a policy is chosen.

### Existing Office CRUD status

Only a partial Office implementation exists:

- `OfficeRepository` exists.
- `OfficeService.saveOffice` exists.
- `OfficeController` exposes only `POST /api/office/save`.
- There are no Office list, get-by-ID, update, or delete controller endpoints.

The current delete method has a logic error:

```java
if (getOneOffice.isEmpty()) {
    officeRepo.deleteById(getOneOffice.get().getId());
}
```

The code calls `get()` when the Optional is empty, which throws `NoSuchElementException`. The condition must be `isPresent()` or, more clearly, use `orElseThrow`.

There is also a repository signature mismatch:

```java
Optional<Office> findByNameAndOfficeNumber(String name, String officeNumber);
```

`officeNumber` is an `int` field, so the method parameter should be `int`, not `String`.

## 3. Recommended API design

Use conventional REST endpoints rather than action names such as `/save`:

| Entity | Create | Read all | Read one | Update | Delete |
|---|---|---|---|---|---|
| Doctor | `POST /api/doctors` | `GET /api/doctors` | `GET /api/doctors/{id}` | `PUT /api/doctors/{id}` | `DELETE /api/doctors/{id}` |
| Office | `POST /api/offices` | `GET /api/offices` | `GET /api/offices/{id}` | `PUT /api/offices/{id}` | `DELETE /api/offices/{id}` |
| Patient | `POST /api/patients` | `GET /api/patients` | `GET /api/patients/{id}` | `PUT /api/patients/{id}` | `DELETE /api/patients/{id}` |

Use UUID path variables because all three entities use UUID primary keys.

Typical status codes:

- `201 Created` after a successful create.
- `200 OK` after a successful read or update.
- `204 No Content` after a successful delete.
- `400 Bad Request` for invalid input.
- `404 Not Found` when an ID does not exist.
- `409 Conflict` when a delete violates a relationship or uniqueness rule.

## 4. First fix the entity classes

### 4.1 Add missing ID accessors

`Doctor` and `Patient` currently do not expose their generated IDs. Add:

```java
public UUID getId() {
    return id;
}
```

An ID setter is normally unnecessary because the database/Hibernate generates it.

Because Doctor owns the Doctor–Office relationship, also add these accessors to
`Doctor` so the service and controller can assign an office:

```java
public Office getOffice() {
    return office;
}

public void setOffice(Office office) {
    this.office = office;
}
```

### 4.2 Prefer `java.time.LocalDate`

Replace `java.sql.Date` with `java.time.LocalDate`:

```java
import java.time.LocalDate;

@Column(name = "date_of_birth", nullable = false)
private LocalDate dateOfBirth;
```

Then update the getter and setter to use `LocalDate`. Jackson handles ISO JSON dates such as `"2000-05-20"` naturally.

### 4.3 Add validation constraints

Add this dependency to `pom.xml`:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>
```

For example:

```java
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;

@NotBlank
@Column(name = "first_name", nullable = false)
private String firstName;

@NotBlank
@Column(name = "last_name", nullable = false)
private String lastName;

@NotNull
@Column(name = "date_of_birth", nullable = false)
private LocalDate dateOfBirth;
```

Add `spring-boot-starter-validation` to `pom.xml`, then use `@Valid` in controllers.

### 4.4 Prevent JSON recursion

The bidirectional relationships can cause infinite JSON serialization. For a quick learning-project fix, do not serialize the reverse collections:

```java
// In Doctor.java
@JsonIgnore
@OneToMany(mappedBy = "doctor")
private List<Appointment> appointments = new ArrayList<>();

// In Patient.java
@JsonIgnore
@OneToMany(mappedBy = "patient")
private List<Appointment> appointments = new ArrayList<>();

// In Office.java
@JsonIgnore
@OneToOne(mappedBy = "office")
private Doctor doctor;
```

For a production-quality API, use request/response DTOs instead of exposing JPA entities directly. DTOs are preferable because they prevent clients from changing relationships accidentally and avoid lazy-loading/recursion problems.

## 6. Implement services

Services centralize business rules and translate missing database rows into useful errors.

### 6.1 Doctor service

Create `DoctorService.java`:

```java
package kigali.clinic.rw.service;

import java.util.List;
import java.util.UUID;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import kigali.clinic.rw.domain.Doctor;
import kigali.clinic.rw.repository.DoctorRepository;

@Service
@Transactional
public class DoctorService {
    private final DoctorRepository repository;

    public DoctorService(DoctorRepository repository) {
        this.repository = repository;
    }

    public Doctor create(Doctor doctor) {
        return repository.save(doctor);
    }

    @Transactional(readOnly = true)
    public List<Doctor> findAll() {
        return repository.findAll();
    }

    @Transactional(readOnly = true)
    public Doctor findById(UUID id) {
        return repository.findById(id)
                .orElseThrow(() -> new ResourceNotFoundException("Doctor not found: " + id));
    }

    public Doctor update(UUID id, Doctor input) {
        Doctor existing = findById(id);
        existing.setFirstName(input.getFirstName());
        existing.setLastName(input.getLastName());
        existing.setDateOfBirth(input.getDateOfBirth());
        existing.setOffice(input.getOffice());
        return repository.save(existing);
    }

    public void delete(UUID id) {
        Doctor doctor = findById(id);
        repository.delete(doctor);
    }
}
```

The `update` method loads the existing entity first. This prevents a client from silently creating a new row when it sends an unknown ID.

## 7. Implement controllers

The three controllers are structurally identical. The following complete example is for Doctor.

### `DoctorController.java`

```java
package kigali.clinic.rw.controller;

import java.net.URI;
import java.util.List;
import java.util.UUID;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;
import jakarta.validation.Valid;
import kigali.clinic.rw.domain.Doctor;
import kigali.clinic.rw.service.DoctorService;

@RestController
@RequestMapping("/api/doctors")
public class DoctorController {
    private final DoctorService service;

    public DoctorController(DoctorService service) {
        this.service = service;
    }

    @PostMapping
    public ResponseEntity<Doctor> create(@Valid @RequestBody Doctor doctor) {
        Doctor saved = service.create(doctor);
        return ResponseEntity
                .created(URI.create("/api/doctors/" + saved.getId()))
                .body(saved);
    }

    @GetMapping
    public List<Doctor> findAll() {
        return service.findAll();
    }

    @GetMapping("/{id}")
    public Doctor findById(@PathVariable UUID id) {
        return service.findById(id);
    }

    @PutMapping("/{id}")
    public Doctor update(@PathVariable UUID id,
                         @Valid @RequestBody Doctor doctor) {
        return service.update(id, doctor);
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> delete(@PathVariable UUID id) {
        service.delete(id);
        return ResponseEntity.noContent().build();
    }
}
```

### Patient and Office controllers

Copy the same controller structure and change:

- `DoctorController` → `PatientController` or `OfficeController`.
- Base path → `/api/patients` or `/api/offices`.
- Entity type → `Patient` or `Office`.
- Service type → `PatientService` or `OfficeService`.
- Service method calls to the corresponding service.

Remove the old `/save`-only Office controller or replace it with the conventional controller above. If backwards compatibility is required, temporarily keep `/api/office/save` as an additional endpoint.

## 8. Add consistent error handling

Create `GlobalExceptionHandler.java`:

```java
package kigali.clinic.rw.controller;

import java.util.Map;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import kigali.clinic.rw.service.ResourceNotFoundException;

@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<Map<String, String>> handleNotFound(
            ResourceNotFoundException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(Map.of("error", ex.getMessage()));
    }
}
```

Without this handler, missing records may result in an unhelpful generic server error. With it, clients receive a clear `404` response.

## 9. Relationship and deletion policy

Doctor and Patient are referenced by Appointment. Before enabling deletion, choose one of these policies:

### Option A: reject deletion when appointments exist

This preserves medical history. Check for appointments in a repository, then throw a conflict exception if any exist. This is usually the safest policy.

### Option B: soft delete

Add a field such as `active` or `deletedAt` and hide inactive records from normal queries. This preserves historical appointments while making the doctor or patient unavailable for new bookings.

### Option C: cascade deletion

Delete appointments together with the doctor or patient using cascade/orphan removal. This is generally inappropriate for medical records and should not be used without a clear data-retention requirement.

For this project, **soft delete or reject deletion** is preferable to cascading appointment deletion.

Also note that assigning an office to a doctor should update the owning side:

```java
doctor.setOffice(office);
doctorRepository.save(doctor);
```

Changing only `office.setDoctor(doctor)` will not update the `office_id` foreign key because Doctor owns the relationship.

### Implemented service-layer restrictions

The service layer now applies the following rules before calling the repositories:

| Operation | Restriction | Result when violated |
|---|---|---|
| Create/Update Office | `officeNumber` must be unique | `409 Conflict` |
| Assign Office to Doctor | The referenced Office must exist | `404 Not Found` |
| Assign Office to Doctor | An Office cannot be assigned to two Doctors | `409 Conflict` |
| Delete Office | An Office assigned to a Doctor cannot be deleted | `409 Conflict` |
| Delete Doctor | A Doctor referenced by an Appointment cannot be deleted | `409 Conflict` |
| Delete Patient | A Patient referenced by an Appointment cannot be deleted | `409 Conflict` |
| Update Doctor | An existing office assignment cannot be silently removed by sending `office: null` | `409 Conflict` |

The implementation is in `DoctorService`, `OfficeService`, and `PatientService`. `AppointmentRepository`
uses `existsByDoctorId` and `existsByPatientId` so the service can reject destructive operations
without loading every appointment into memory. `GlobalExceptionHandler` converts these business
exceptions to consistent `404` and `409` JSON responses.

The Doctor–Office relationship is deliberately updated from the Doctor side because Doctor owns
the foreign key. A request that assigns an office must provide an existing office ID, for example:

```json
{
  "firstName": "Amina",
  "lastName": "Uwase",
  "dateOfBirth": "1988-04-12",
  "office": { "id": "existing-office-uuid" }
}
```

If the application needs to release an office, implement an explicit service operation such as
`unassignOffice(doctorId)` rather than treating a missing field in a general update as a deletion.
This makes the relationship change intentional and auditable. The current delete policy preserves
appointment history; a production system may replace the rejection with soft deletion.

## 9.1 Appointment CRUD

Appointments are exposed through `AppointmentController`:

| Method | Endpoint | Behavior |
|---|---|---|
| `POST` | `/api/appointments` | Creates an appointment; Doctor and Patient IDs must refer to existing records. |
| `GET` | `/api/appointments` | Lists appointments. |
| `GET` | `/api/appointments/{id}` | Returns one appointment or `404`. |
| `PUT` | `/api/appointments/{id}` | Updates a mutable appointment and validates both relationships. |
| `DELETE` | `/api/appointments/{id}` | Deletes only a scheduled or confirmed appointment. |

The service defaults a missing status to `SCHEDULED`. `COMPLETED` and `CANCELLED` appointments
are treated as historical records: they are read-only and cannot be updated or deleted. This
prevents changing medical history after completion or removing evidence that an appointment was
cancelled. If a cancellation is needed, update a `SCHEDULED` or `CONFIRMED` appointment by setting
its status to `CANCELLED`.

Appointment requests should reference relationships by ID rather than embedding new entities:

```json
{
  "appointmentDate": "2026-10-05",
  "reason": "Routine consultation",
  "status": "SCHEDULED",
  "doctor": { "id": "existing-doctor-uuid" },
  "patient": { "id": "existing-patient-uuid" }
}
```

The `AppointmentService` resolves both IDs through their repositories before saving, so a client
cannot create an appointment pointing to a nonexistent Doctor or Patient.

## 12. Important issues found in the uploaded project

- `DoctorRepository` contains an unused `javax.print.Doc` import.
- Doctor and Patient have no `getId()` method.
- Office delete logic checks `isEmpty()` and then calls `get()`, which is incorrect.
- `findByNameAndOfficeNumber` uses `String officeNumber` even though the entity field is `int`.
- Only Office create is exposed; Doctor and Patient have no repository/service/controller layers.
- There is no validation or global exception handling.
- Bidirectional JPA relationships can cause recursive JSON responses.
- Entities are used directly as request and response bodies; DTOs are safer for a real API.
- Deletion behavior for entities referenced by appointments is undefined.
- The database password is stored in plain text in `application.properties`.
- The current environment has Java 21 but no Java compiler, so the Maven build cannot complete until a JDK is installed.

The implementation order should therefore be: **fix entity and repository issues → add Patient repository → implement the three services → implement the three controllers → add validation/error handling → decide relationship deletion rules → test all endpoints**.
